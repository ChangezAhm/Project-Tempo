This is a promising architecture that has demonstrated the core capability — the model-perceives/code-verifies inversion measurably works, workbook-specific hard-coding is near zero, and verification is unusually deep — but generalisation rests on three template families, the accuracy numbers were largely hand-verified rather than system-computed, the orchestrator is a 1,651-line god-file, and the entire last 72 hours of work (82 files) is uncommitted on top of a two-week-old git HEAD. It is neither a patch collection (C) nor adequately evidenced (so D applies to the external claims, not the architecture).

§1 · Does it work end-to-end?

Q1 — the production path. Green One coherent chain exists and runs: upload (Next.js app/api/v1/templates/route.ts → Supabase) → parse (app/pipeline.py: parse_and_persist, Aspose → gzipped snapshot) → L2 structure (app/structure/detect.py) → L3 understanding (app/understanding/workbook.py: understand_workbook, per-sheet Opus + grid + image, deterministic graph verify) → data model (app/datamodel/derive.py: derive_data_model, v19) → populate (app/population/run.py: _run_population: grids → one-pass or claims+grid mapping → reconcile → catalogue → contract overlay → verify → repair → execute → outcome revision → tie-out loop → apply → render → checks) → deliverables (render_filled + linked.py traceable variant).

Q2 — overlapping pipelines. Amber Three mapper variants coexist in mapping.py: legacy digest batching (Sonnet, text-only), grid batching, and one-pass — selected by TEMPO_MAPPER, plan-cache state, and a ≤80-metric gate in run.py. All are live fallbacks of each other. Defensible as a fallback ladder; undeniably three code paths to maintain, and the legacy path's behavior is what most old tests pin.

Q3 — swallowed failures. Amber By design, ~20 except Exception blocks in run.py convert stage failures to warnings so "verification must never sink a fill" (e.g. conservation, revision, tie-out loop, audit upload, additions). Each logs and most stamp routing, but a user reading only the fill report will not see, e.g., a failed audit upload. The two hard exceptions that correctly propagate: SpendCapExceeded and torn-model refusal.

Q4/Q5 — can it deliver anyway / what hard-stops. Amber Hard stops today: no data model derivable; torn data model (build_demand, run.py ~545); spend cap. Everything else — failing template checks, ambiguous mappings, unparsed sheets — delivers with flags: red tie-out banner (page.tsx), review questions, geometry flags. That is a deliberate product choice ("deliver + loud flags"), but note: a user who ignores the red banner can still submit a failing workbook. Delivery is never blocked on check failure.

Q6 — traceable recompute enforcement. Green Genuinely enforced: linked.py: attach_source_links per-cell cell.calculate() compares each formula's computed value to the written value (_values_agree, rel-tol 1e-6); mismatches revert to the raw value and are counted (fallback_cells, mismatches). Tests: test_linked.py: test_linked_mismatch_falls_back_to_raw_value. Both live pack runs report fallback_cells: 0, verified: true.

§2 · Generalising or patching? (the key section)

Q7/Q8 — workbook-specific logic count. Green, with an amber asterisk Grep across parser/app for every known workbook/sheet/company name (Mgmt_Accounts, Flash, Chronograph, Nordvent, IPV, aurora…): 7 hits, all comments or eval anchors; zero in executable logic. The one name in derive.py:526 is a comment. Hand-verified truths live only in eval/corpus.py (class B: legitimate test knowledge). The asterisk: specialisation lives instead in general rules with uncalibrated constants — 14 compiled lexicon patterns in priors.py, 9 period regexes in temporal_analyzer.py, and ~11 magic thresholds sampled in three files alone (series-recovery cap 60, one-pass gate 80, Opus tier 100, cache-estimate ÷8, positional shape ×3, claims-gate ×1.3). Every one is class A in form but was tuned against n≤3 workbooks. Class C (workbook hacks): none found.

Q9/Q10 — abstractions vs conditionals; trend. Amber Recent fixes are genuinely general in shape (orientation as a first-class concept in catalogue.py: claim_orientation; the finest-sub-grain bridge in periods.py: align_slot; conservation over the source's own formula graph). But the count of guard-rules is accelerating — reconciler plausibility bounds, collapse belts, shape guards, fiscal flags all landed in one week. Each is defensible; together they are a growing constant-tuning surface that the dead-then-revived eval net only recently started watching.

Q11 — what generalises to an unseen pair tomorrow. Parsing, snapshotting, L3 understanding, grid building, mapping, verification, tie-out loop, plan caching: automatic. What won't: long-format tables (flagged + skipped, claim_orientation → "unknown"), fiscal re-bucketing (flags + asks, never re-buckets), any layout whose period identity the L2/L3 chain misses (whole-sheet zero, now at least loudly flagged in derive.py).

Q12/Q13/Q14 — shape support matrix. Explicitly represented shapes: classic G, transposed G (Series.transposed, series_cell()), monthly/quarterly/annual grains incl. quarter→year bridge G, fiscal years A (detected + flagged, not re-bucketed), categorical/covenant tables A (protected from garbage, not populated), long-format TB R (skipped), multi-block sheets A (untested beyond L3's sections), merged cells/hidden geometry/formulas/named ranges G (snapshot-level, workbook_parser.py), bridge tables R (nothing explicit). Shape is now partially explicit (orientation, grain, fiscal_start on Series) — a real architectural asset — and a shape fix does transfer to unrelated templates (the transposed fix required zero template knowledge). Q14: yes, with the eval net now enforcing non-regression.

§3 · AI vs deterministic separation

Q15–18. Green — converged this week, with two exceptions. LLM decides: sheet meaning, roles, definitions (L3); source structure claims; metric↔series meaning + fill semantics (rollup/units/sign/scenario) (mapping.py); orphan placement; revisions. Code decides: every address, value, scale factor, period alignment, double-count, conservation, check evaluation. Exceptions where code still infers meaning: priors.py lexicons classifying config/placeholder labels, and reconcile._scen_of reading basis-row words — both flagged-prior style but still semantic inference in code (Q16). Q17 inverse: LLM self-reported confidence gates fills at 0.6 (verify.py:94) — an uncalibrated model opinion acting as a hard threshold (see Q39).

Q19 — can context still hide information? Amber Yes, in bounded and now-announced ways: grids.py caps (120k chars/sheet, 400k total → row-summary mode with banners + grid_notes), reconciler series-recovery cap 60/sheet (reported), one-pass output squeeze (detected via degraded, claims replaced from cache/per-sheet pass). The silent-truncation class was the root of two majors and is now instrumented rather than eliminated.

Q20/Q21 — what stops bad mappings. Fabricated refs: translate_sources resolves label-cells against the catalogue index, unresolvables become visible unavailables; apply.py reads only real snapshot cells and refuses formula/error strings (apply.py:101). Periods: align_slot date-bucket matching, never cross-grain without declared rollup. Signs: plan sign cross-checked against template evidence (execute.py:_dominant_sign). Double counting: verify.py DOUBLE_COUNT with formula-graph scoping. Units: declared-vs-magnitude reconciliation (_resolve_scale). Scenario: strict tag matching + explicit contract equivalence only. Subtotal-vs-component: conservation families + template value_role guard. Q21: no path exists where an LLM-emitted number becomes ground truth — the model never outputs values, and apply.py reads all values from the snapshot. That claim survives inspection.

Q28–30. Provenance: strong at run level — every audit stores plan, links, issues, notes per run (run.py audit dict), and per-cell notes name their evidence — so "why this mapping" is answerable from a stored audit for that run; decision-level versioning is just review-item timestamps. Q30 Amber: chain reconstructable, not first-class.

§5 · Verification strength

Q31–36. Green — this is the strongest layer. Deterministic, post-mapping: plan verify (8 typed issue codes, verify.py); execute-time scale/sign/period cross-checks; apply-time value guards; conservation families; sign-convention checks (checks.py); the template's own Excel check formulas evaluated pre-deliverable and again at render (template_checks.py + tie-out loop, run.py ~1027); per-cell traceable-formula recompute (linked.py); torn-model write verification (supabase_client.replace_data_points). LLM-based checks: none — verification is fully deterministic. Q34: check failure → one bounded model revision → re-verify → red UI banner + review item; delivery proceeds flagged. Q36: reconciliation exists exactly where the template's authors put check formulas — EBITDA/cash/BS-balance ties ride on the template's own checks, which is elegant but means a template without a Checks sheet gets no financial-level reconciliation (bare grids tie only by construction).

Q37–39. Missing-data vs failed-to-find: partially distinguished — coverage_summary now states date-range gaps in plain words, and unmatched reasons separate "no source column for this period" from "no source series mapped"; but "the source lacks it" vs "the catalogue missed it" is only as reliable as the catalogue, and the trial-balance under-cataloguing incident shows that boundary failing. Q39: confidence is raw LLM self-report gating at 0.6 — never calibrated against outcomes. Red on calibration.

Q40 — remaining silent-wrong-number paths. Honest enumeration: (1) a mapping that is semantically wrong but arithmetically self-consistent on a template without check formulas (nothing ties it); (2) the flagged-default ladder — source-basis scale assumption, budget⇐forecast equivalence — is visible in notes/questions but the numbers land; a user not reading flags sees them as clean; (3) positional alignment on genuinely dateless templates (flagged, still a guess); (4) stale answered decisions after label changes. All are flagged-somewhere; none are silent-in-audit; (1) is the real exposure.

Q52–56. Red on evidence discipline. Accuracy figures were computed by the engineer's in-session scripts, not by a system-owned scorer; "fillable" denominators are estimates; ground truth exists only for the two controlled packs (self-authored). Best defensible metric today: zero unflagged wrong numbers + per-run tie-out pass rate, not a fill percentage. Sample size before claiming "98% of fillable" externally: ≥20 real template×pack pairs across ≥8 sponsors, scored by an automated harness against human-marked ground truth — the harness partially exists (eval/label_ingest.py, owner's 1/2 marking scheme) but hasn't been run on the new pipeline. Defensible today on a fully unseen pair: ~70–90% of fillable on first run, with wrong-number risk concentrated in check-less templates — anything tighter is not supported by n=3.

§10 · Production readiness

Q73–84. Red — and known. Concurrency: per-template in-process lock only; two simultaneous users on different templates share one sync uvicorn worker. Jobs: not queued; resumable only via the new plan/understanding caches (real, but caches live in the OS temp dir — source_cache._DIR — wiped on reboot, not multi-tenant). Idempotency: run-stamped storage avoids overwrites (new); DB writes are replace-with-verify. Retries: chunked DB writes retry (new); LLM calls retry once on parse, thinking-fallback on truncation; provider timeout mid-call → run fails, resumable from plan cache. Observability: LangSmith tracing per call with sites + spend guard actuals (cost by run/stage/model: yes; by customer: no customer concept). Security: no auth anywhere, permissive RLS ("MVP" migrations), service-role key in .env, an API key gate on the parser, a dev route that shells open downloaded files (open-local), and API keys that were once pasted into chat (rotation flagged in memory, unverified). Financial data goes to the LLM by design (grids) — acceptable if disclosed; logs are mostly clean of values. Biggest weaknesses: auth/RLS, open-local, temp-dir caches, uncommitted tree.

§11 · Cost/performance

Q85–92. Latency: onboarding ≈ 60% per-sheet Opus generation (output-token bound), 15% serial Aspose renders, rest synthesis/persist/regions; populate ≈ 70% mapping-model output + revision loops, 15% renders/checks. Cost dominators: Opus output tokens (mapping entries, per-sheet L3 dumps) — input is now largely cache-priced (llm.py cache_blocks, real 1.25×/0.1× accounting in the guard). Caching: understanding by content-hash, plans two-stage, prompt-prefix ephemeral, template snapshots — appropriate; the remaining repeated-information smell is re-deriving catalogues every run (cheap, deterministic, fine). The $8–12/first-run target is arithmetically supported (tiering + caching are in code, not yet user-proven on the big template). At 50 companies × monthly: LLM ≈ 50×($10 first + ~$2×re-runs) ≈ $600–900/mo — trivial; the binding constraint is the single-process architecture, not money. Infra cost is a rounding error; wall-clock throughput is the real limit (~3 runs/hour today).

§12 · Strategic assessment

Q93. B (detailed in the verdict box above). Against C: zero workbook-named logic in production code, shape fixes provably transferred (transposed fix needed no template knowledge), and the rule ledger discipline exists even if this week ignored it. Against A: three template families, constants tuned on them, two shape classes unsupported. D applies narrowly: the external accuracy claims outrun the evidence; the architecture claims do not.

Q94/95. Trending easier, with evidence: pack B (transposed, fiscal, quarterly) initially cost a full engineering day; its fixes were all general (orientation, bridge, guards) and the third pack's autopsy reused them unchanged — its new failures were different classes. Counter-evidence: every new pack so far has surfaced ≥1 new class, and the week added ~10 tuned constants. Honest read: the kind of work per pack is shrinking (from rebuilds to guards), the presence of work per pack is not yet zero.

Q96–98 — the 20-pair experiment. Freeze the code. Run 20 real template×pack pairs (≥8 sponsors, include long-format TBs and check-bearing templates). For each, auto-score against human-marked ground truth (the existing 1/2 marking harness), and record: fillable-correct %, unflagged wrong numbers, tie-out pass rate, engineering interventions needed. Keep building if: median ≥85–90% fillable-correct, zero unflagged wrong numbers, and interventions per pair decline monotonically over the sequence. Stop and rethink if: any silent wrong number recurs after the tie-out loop, or interventions stay flat across pairs 10–20 (that is the patch-treadmill signature), or fillable-correct varies wildly (<60% on >25% of pairs).

Q99 — three changes in one month. (1) The 20-pair evaluation harness with automated cell-level scoring — turns every claim into a measurement and every failure into an anchor. (2) Decompose _run_population into an explicit, individually-tested staged pipeline with persisted stage state — fixes maintainability, resumability, and the orchestrator-coverage hole at once. (3) Commit, CI, auth, and durable caches — the unglamorous production floor.

Q100. Productive at reducing fundamental risk — genuinely, but unevenly. The two existential risks (silent wrong numbers; an architecture that couldn't perceive real workbooks) were both materially reduced this week, with measured before/after evidence. What grew alongside: orchestrator complexity, three mapper variants, uncalibrated constants, and an evidence deficit on the accuracy claims. The work moved the product from "impressively wrong sometimes" to "honest, verified, and slow to trust itself" — the right direction — but the next month must be spent on evidence and consolidation, not new capability, or the complexity added this week becomes next month's incident source.
